# 2026-11-16 학습 모듈 재설계와 통합 클라우드 저장 검토

- 일시: 2026-11-16 (Asia/Seoul)
- 상태: 사용자 제약 확정 · 데이터 모델과 구현 순서는 AI 설계 제안
- 선행 기록: 포스트잇 러너 참조 조사
- 작업 범위: 분석 및 기록만. 원본 코드 복사·실행 코드 수정·SQL 적용·클라우드 접속·데이터 이전 없음

## 사용자에 의해 확정된 기준

1. 코르크·포스트잇 표현은 MIG DOT 개발원칙을 따라야 하며 분석과 개선 대상이다. 원형 보존을 우선하지 않는다.
2. 모듈 화면 분리와 URL 기반 탐색을 적용한다.
3. 스타일의 우선 기준은 MIG DOT다. 통합을 위해 기존 화면·스타일을 다시 설계할 수 있다.
4. 앱의 영속 운영 데이터는 단일 Supabase 프로젝트에 통합하고 개인용 운영에도 인증·인가를 적용한다.

기존 조사에서 제안한 ‘보드 경험 유지’와 ‘로컬/클라우드 선택’을 통합본의 확정 기준으로 해석하지 않는다. 아래 재설계가 후속 작업의 우선 기준이다.

## UI 재평가

겹친 카드, 기울기와 질감은 제목 탐색·키보드 포커스·모바일 터치를 방해하는지 검증한다. 읽기 쉬운 목록/그리드를 기본 후보로 두고, 코르크 보드 표현은 사용 가치가 확인될 때 보조 보기로 검토한다. 이 선택은 아직 UI 시안으로 확정하지 않았다.

MIG DOT의 공통 내비게이션, 색상 역할, 글자 위계, 버튼과 폼 기준을 적용한다. 원본 전역 CSS는 그대로 가져오지 않는다. 모듈 전용 표현은 범위를 격리하고 공통 셸을 덮어쓰지 않는다.

## 기존 저장 방식의 분석

원본은 로컬 localStorage 또는 사용자별 JSON 문서 1행으로 저장한다. 클라우드 구현은 revision 비교, 서버 사용자 식별, 비공개 이미지와 서명 URL이라는 장점이 있다. 반면 기록 한 장의 변경에도 전체 문서를 전송하고, 다른 학습 대상의 변경도 같은 revision에서 충돌한다. 개별 기록의 제약·조회·검색·페이지 처리 및 소유권 관계를 DB에서 관리하기 어렵다.

통합 클라우드가 모든 모듈의 데이터를 단일 테이블/JSON 문서에 넣는다는 뜻은 아니다. 하나의 Supabase 프로젝트·Auth·DB·Storage를 공유하고, 데이터 테이블 및 접근 코드는 모듈별로 분리하는 방식을 제안한다. 문서 원본 Markdown의 Git 관리 정책은 유지한다. 비공개 운영 데이터와 사진·비밀값을 번들 Markdown에 넣지 않는다. 문서 자체도 비공개 저장·배포해야 하는 요구가 있으면 정적 번들과 별개의 접근 제어 설계를 검토해야 한다.

## 제안 데이터 모델

| 저장 위치 | 역할 | 주요 필드 |
|---|---|---|
| Supabase Auth의 auth.users | 공통 사용자 식별 | 플랫폼 관리 사용자 ID |
| public.learning_topics | 학습 대상별 행 | id, owner_id, name, description, image_path, next_color_index, version, created_at, updated_at |
| public.learning_notes | 기록별 행 | id, owner_id, topic_id, title, body, tag, color, image_path, version, created_at, updated_at |
| 비공개 learning-images 버킷 | 원본 사진 및 썸네일 | 사용자ID/모듈명/임의파일명 |

필드와 명칭은 설계안이다. 코드 및 마이그레이션은 아직 없다. 모든 모듈을 위한 범용 JSON 테이블, 미사용 프로필/권한 시스템은 만들지 않는다.

owner_id는 공통 Auth ID를 참조한다. learning_topics에 (id, owner_id) 유일 제약을 두고 notes의 (topic_id, owner_id)가 이를 참조하게 하여 다른 사용자의 학습 대상에 기록을 붙이는 것을 DB 제약으로도 막는다. 제목 길이, 허용 색상, 필수 필드 및 참조 무결성은 DB에서도 검증한다. 소유자와 학습 대상별 조회에 맞는 인덱스 및 정렬/페이지 조회를 도입한다. 대상 삭제 정책은 실제 기능 범위와 함께 결정하고 이미지 파일까지 SQL cascade로 삭제된다고 가정하지 않는다.

## 인증과 인가

- 로그인과 세션은 MIG DOT 공통 서비스가 소유하고 모듈은 동일 클라이언트·사용자 ID를 사용한다. 각 모듈에 별도 계정·로그인을 만들지 않는다.
- 개인용 초기 운영은 서버의 공개 신규 가입과 익명 로그인을 끄고 운영자가 만든 본인 계정만 사용하도록 제안한다. 로그인 방식 세부 선택과 세션 만료·복구 UX는 구현 시 결정한다.
- 로그인 화면과 라우트 보호는 UX다. 실질 접근 제한은 DB 권한과 RLS, Storage 정책에서 시행한다.
- 데이터 테이블은 RLS를 활성화한다. anon에는 운영 데이터 접근 권한을 주지 않고 authenticated에도 필요한 작업만 grant한다.
- SELECT/DELETE는 auth.uid() = owner_id인 행만 허용한다. INSERT는 WITH CHECK로 소유자를 검증하고 UPDATE는 기존 행의 USING과 변경 후 WITH CHECK를 모두 검증한다. 요청에 사용자 ID가 들어왔다는 이유만으로 신뢰하지 않는다.
- 본인만 사전 등록한 현재 범위에는 복잡한 RBAC가 필요하지 않다. 향후 같은 Auth에 다른 목적의 계정을 수용하면 owner 검사 외에 승인 사용자/모듈 이용 권한도 도입한다. authenticated 역할 자체를 관리자 권한으로 사용하지 않는다.
- publishable key만 클라이언트에 두고 secret/service_role 키를 넣지 않는다. SQL Editor/관리자 권한으로 성공한 조회는 일반 사용자 RLS 검증으로 간주하지 않는다.

## 사진 저장과 권한

이미지 바이너리는 Storage에, 파일 경로는 DB에 둔다. 데이터 URL 및 만료되는 서명 URL은 영속 DB 필드에 저장하지 않는다. 비공개 버킷 정책은 버킷과 본인 경로를 함께 검증하고 업로드 형식·크기를 제한한다. 이미지 참조 경로도 해당 사용자 범위인지 검사한다.

표시할 때만 짧은 수명의 서명 URL을 발급한다. 서명 URL은 유효기간 동안 링크 소지자가 사용할 수 있으므로 로그아웃만으로 즉시 무효화된다고 가정하지 않는다. 이미지 업로드와 DB 저장은 하나의 트랜잭션이 아니므로 실패한 업로드·응답 유실·삭제 파일의 정리와 재시도를 설계한다. Storage 객체는 Storage API로 삭제한다. 반복 저장마다 변하지 않은 모든 사진의 서명 URL을 재발급하는 구조는 피한다.

## 저장과 여러 기기 변경

전체 작업공간 revision 대신 기록/대상별 version 비교 저장을 제안한다. 같은 기록의 동시 편집은 충돌로 처리하고, 다른 기록의 변경은 불필요하게 충돌시키지 않는다. version 조건부 갱신 결과가 0행인 경우 권한·삭제·충돌 등 원인을 구분해 재조회와 재시도 흐름을 제공한다. 저장 성공 응답 전에는 완료 표시를 하지 않는다.

새 기록 생성과 색상 순서 증가처럼 함께 성공해야 하는 작업은 서버 트랜잭션의 좁은 RPC로 묶는다. 이 RPC도 소유권 검사와 동시성 제어가 필요하다. 기본 invoker 권한을 검토하고 definer가 필요한 경우 권한·search_path·사용자 검증을 별도로 검토한다. 초기에는 화면 복귀와 수동 조회 등 최소 동기화부터 제공하고 Realtime은 실제 필요성으로 결정한다. 자동 충돌 병합이나 오프라인 큐는 이번 설계의 기본 범위로 두지 않는다.

## 로컬 저장과 이관

Supabase를 영속 운영 데이터의 단일 원본으로 사용한다. 모듈에서 localStorage로 자동 전환하지 않는다. 서버 미설정·만료 세션·네트워크 오류·빈 계정은 구분해 안내하고 저장이 가능한 것처럼 보이지 않게 한다. 로그인한 사용자의 데이터는 기본적으로 메모리에서 보유하고 로그아웃/사용자 변경 시 비운다. 세션은 SDK가 관리하므로 ‘브라우저에 아무것도 저장하지 않는다’고 표현하지 않는다.

기존 JSON 내보내기를 일회성 데이터 이관의 입력으로 활용할 수 있다. 검증·미리보기·ID 충돌 처리·사진 업로드·부분 실패 복구를 마련하고, 서버 저장 결과를 확인한 뒤 이관 완료로 표시한다. 반복 이관이 기록을 중복 생성하지 않도록 한다. 기존 브라우저 데이터와 원본 서비스는 자동 삭제하지 않는다. 백업의 완성은 내보내기 성공뿐 아니라 복원 검증까지 포함한다.

## 구현 순서 및 완료 기준

공통 인증·세션과 개인 사용자 접근 정책 → 테이블·Storage·RLS 마이그레이션 → 소유권 및 여러 기기 충돌 검증 → 원칙에 맞춘 학습 모듈 화면·라우팅 → 기존 데이터 가져오기와 백업·복원 순서로 진행할 것을 제안한다.

완료 전에 비로그인, 다른 사용자, 만료된 세션, 소유자 위조 INSERT/UPDATE, 다른 사용자의 topic 참조, 직접 API 요청, 사진 경로 접근, 같은/다른 기록의 동시 저장, 네트워크 실패와 이미지 정리를 테스트한다. UI의 메뉴 숨김이나 저장소 모형 테스트만으로 접근 제어가 검증됐다고 판단하지 않는다. 원본 코드와 클라우드는 이번 작업에서 변경하지 않았다.
