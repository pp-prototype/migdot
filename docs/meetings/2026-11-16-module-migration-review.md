# 기존 프로젝트 모듈 이식 검토

- 논의일 2026-11-16 (Asia/Seoul)
- 상태 AI 검토·제안 초안 · 이식 대상과 실행 범위 미확정
- 근거 기존 사이드 프로젝트 및 GitHub 프로젝트를 MIG DOT 모듈의 기반으로 사용하는 방법 문의

## 배경과 목적

이미 만든 앱의 기능과 코드를 활용하여 MIG DOT 내부에서 사용할 완성된 모듈로 통합하는 경로를 검토한다. 이번 검토에서 실제 프로젝트 복사, 원격 저장소 접근, 데이터 변경은 진행하지 않았다.

## 확인한 사항

로컬 형제 프로젝트의 package.json에서 execution-tracker, meta-wallet, post-it-learner, miso-backoffice는 React를 사용한다. bullet-journal 및 what-i-learned-receipt의 루트 package.json에서는 React 의존성이 확인되지 않았다. 이는 기술 스택의 예비 확인이며 내부 구현이나 이식 난이도 전체를 평가한 결과는 아니다.

현재 MIG DOT의 modules.ts는 회의록·업데이트·문서 경로를 등록한다. 홈의 개인용 앱 영역은 아직 빈 상태로 고정되어 있다. 실제 앱을 이식할 때 앱과 기록 페이지를 구분하는 등록 정보 및 홈 목록 연결이 추가로 필요하다. 공통 Supabase 클라이언트는 있으나 로그인과 데이터 접근 제어는 아직 구현하지 않았다.

## 접근 방식 비교

- 외부 링크 연결: 기존 앱을 그대로 사용할 수 있는 임시 경로. 별도 배포·인증·데이터가 유지된다.
- 필요한 코드와 기능의 내부 모듈 이식: 단일 배포·공통 인증을 지향하는 현재 모듈형 모놀리스에 적합한 기본 제안.
- 독립 저장소를 서브모듈이나 패키지로 연결: 원본과 통합본을 동시에 지속 유지할 필요가 있을 때 검토. 초기 1인 운영에서는 관리 비용을 먼저 평가한다.
- iframe: 기존 페이지를 감쌀 수 있으나 라우팅·스타일·세션을 통합하는 방법과는 다르므로 기본안으로 제안하지 않는다.

## 제안하는 진행 순서

1. 대상 앱 1개와 유지할 핵심 기능을 선정한다.
2. 원본 저장소 주소, 기준 커밋, 로컬 변경 여부, 사용법, 인증·DB·서버 및 데이터 저장 위치를 조사한다.
3. 원본은 보존하고 별도 참조 디렉터리에서 읽는다. GitHub 소스도 먼저 MIG DOT 밖에 체크아웃하여 검토한다.
4. 재사용할 화면·로직·에셋·필요 의존성만 src/modules/<id>/로 이식한다. .git, node_modules, dist, 실제 환경 변수와 개인정보 파일은 가져오지 않는다.
5. 기존 루트 엔트리·라우터·전역 CSS를 공통 셸과 충돌하지 않게 조정하고, 공통 인증과 데이터 접근은 shared를 사용한다. 서버가 필요한 앱은 정적 호스팅 가능 여부를 따로 검토한다.
6. 앱 등록과 홈 카드, 모듈 경로를 연결한다. 임시 데이터를 쓸 경우 실제 데이터와 구분한다.
7. 기존 데이터가 있으면 별도 백업, 데이터 구조와 사용자 ID 대응 검토, 시험 이관 및 복원 검증을 진행한다. 코드 이식과 데이터 이관은 별도 작업이다.
8. 원본 기능과 비교하고 핵심 저장·조회·수정, 새로고침, 모듈 간 스타일 영향, 접근 권한, 모바일 동작을 검증한다.
9. 회의록·업데이트·사용법과 출처 커밋을 기록하고 기존 서비스의 종료 여부는 이관 완료 후 결정한다.

## GitHub 원본과 변경 이력

저장소 전체 복제는 MIG DOT 모듈 통합과 구별한다. 기본 제안은 원본 저장소에 과거 이력을 남기고 MIG DOT에 출처 URL·커밋과 이식 변경 내역을 기록하는 방식이다. 전체 이력 보존이 요구되면 별도 가져오기 전략을 검토한다. 제3자 코드·에셋은 라이선스와 고지 조건을 확인한다.

## 보류 및 후속 작업

첫 이식 대상, 완성본의 기능 범위, 데이터 통합 범위 및 원본의 계속 운영 여부는 미정이다. 분석 후 이식 계획을 작성하며, 현재 대화만으로 기존 데이터 이전이나 원본 서비스 종료를 승인된 것으로 보지 않는다.
