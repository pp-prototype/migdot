# MIG DOT — 시스템 설계 및 개발 원칙서

**문서 버전:** 1.2  
**프로젝트명:** MIG DOT  
**시스템 유형:** 개인용 통합 웹 애플리케이션 플랫폼  
**개발 및 운영:** 1인 개발  
**아키텍처:** 모듈형 모놀리스 (Modular Monolith)  
**운영 목표:** 최소 비용, 모듈 독립성, 지속 가능한 유지보수

## 개발 시작

```sh
nvm use
npm ci
npm run dev
```

개발 환경: Node.js 22.12 이상, npm. Supabase 설정 없이 홈과 문서를 확인할 수 있습니다.

- [시작하기 및 배포 설정](docs/documentations/mig-dot/getting-started.md)
- [모듈 개발 안내](docs/documentations/mig-dot/development.md)
- 검증: `npm run check` / 빌드 출력: `dist/`

현재 구현: 개발 기반, 공통 셸, 모듈 등록·라우팅·오류 경계, 기본 Markdown 문서 조회·검색.
인증, 기존 앱 이식, 문서 계층형 탐색 및 실제 배포 검증은 후속 작업입니다. 아래 1.0 체크리스트는 전체 요구사항의 완료 시점에 갱신합니다.

## 1. 프로젝트 개요

MIG DOT는 개인이 사용하는 여러 웹 애플리케이션을 하나의 환경에서 개발, 배포, 관리하기 위한 통합 웹 플랫폼이다.

각 모듈은 독립적인 기능과 인터페이스를 유지하면서 공통된 인증, 내비게이션, 데이터 관리 및 운영 환경을 공유한다.

### 핵심 목표

1. **통합성:** 모든 모듈이 MIG DOT에 소속되도록 한다.
2. **독립성:** 개별 모듈의 중단과 오류가 다른 모듈에 미치는 영향을 최소화한다.
3. **경제성:** 무료 인프라를 우선 사용하며 월 운영비 0원을 목표로 한다.
4. **확장성:** 기존 시스템의 대규모 수정 없이 모듈을 추가할 수 있도록 한다.
5. **유지보수성:** 1인 개발자가 장기간 관리할 수 있는 구조를 유지한다.
6. **기록성:** 개발 의사결정, 변경 이력 및 현재 기능의 사용 방법을 문서화한다.

## 2. 시스템 아키텍처

모듈형 모놀리스 기반의 통합 웹 애플리케이션을 채택한다.

### 2.1 구성 원칙

- 단일 Git 저장소와 프론트엔드 배포
- 공통 애플리케이션 셸(App Shell)
- 기능별 독립 모듈
- 공통 인증 및 데이터베이스
- 모듈별 UI, 데이터, 비즈니스 로직 분리
- 개발 이력과 사용자 문서의 통합 조회

### 2.2 기술 스택

| 영역 | 기술 |
|---|---|
| 프론트엔드 | React + TypeScript + Vite |
| 스타일링 | Tailwind CSS |
| 라우팅 | React Router |
| DB 및 인증 | Supabase |
| 배포 | Cloudflare Pages |
| 버전 관리 | Git + GitHub |
| 문서 원본 | Markdown |
| 문서 조회 | MIG DOT 내장 문서 모듈 |

기술 스택 변경은 실제 필요와 운영 부담을 검토한 뒤 결정한다.

## 3. 핵심 개발 원칙

### 원칙 1. 모듈 우선 개발

신규 기능은 기본적으로 MIG DOT 내부 모듈로 개발한다.

독립적인 서버, 보안 요구사항 또는 별도 배포 환경이 필요한 경우에만 프로젝트 분리를 검토한다.

### 원칙 2. 모듈 간 결합 최소화

각 모듈은 자체 UI, 상태, 비즈니스 로직을 소유한다.

다른 모듈의 내부 코드에 직접 의존하지 않으며, 공통 기능은 Shared Services를 통해 사용한다.

### 원칙 3. 공통 정체성 유지

모든 모듈은 공통 내비게이션과 MIG DOT 홈 이동 기능을 제공한다.

개별 모듈의 인터페이스와 사용자 경험은 자유롭게 설계한다.

### 원칙 4. 장애 영향 최소화

모듈별 지연 로딩과 오류 경계를 적용한다.

배포 전 빌드와 핵심 기능을 검증하며, 문제가 발생하면 이전 정상 버전으로 복구할 수 있도록 한다.

공통 인프라 장애는 전체 시스템에 영향을 줄 수 있음을 인정한다.

### 원칙 5. 비용 최소화

무료 서비스를 우선 사용하며 유료 서버 및 상시 실행 인프라 도입을 지양한다.

유료 서비스는 무료 대안으로 요구사항을 충족할 수 없을 때만 검토한다.

### 원칙 6. 최소 기능 우선 구현

실제 사용에 필요한 최소 기능부터 구현한다.

사용이 검증되지 않은 기능이나 미래 확장만을 위한 과도한 설계를 지양한다.

### 원칙 7. 데이터 보안 및 지속성

인증 및 접근 권한을 검증하고 비밀키를 클라이언트 코드에 노출하지 않는다.

중요한 데이터의 백업 및 복원 절차를 마련한다.

### 원칙 8. 회의록 리포트 의무 기록

시스템 개발에 관한 주요 논의와 의사결정은 **Meeting Report**로 문서화한다.

회의록은 다음 내용을 포함한다.

- 논의 일시 및 주제
- 논의 배경과 목적
- 주요 의견 및 검토 사항
- 결정 사항과 그 근거
- 보류·기각 사항
- 후속 작업 및 미해결 과제

회의록은 Markdown으로 저장하며 MIG DOT의 회의록 리포트 탭에서 조회할 수 있어야 한다.

AI가 접근 가능한 대화를 기반으로 초안을 생성하고 개발자가 확인하는 방식을 권장한다.

### 원칙 9. 개발 업데이트 의무 기록

기능 추가, 수정, 삭제 및 주요 코드 변경은 **Development Update Report**로 문서화한다.

개발 업데이트는 다음 내용을 포함한다.

- 변경 일시 및 버전·커밋 정보
- 변경 대상 모듈
- 기능 추가·수정·삭제 사항
- 기술적 변경 내용
- 사용자 경험(UX) 변경점
- 호환성 및 기존 기능에 미치는 영향
- 테스트 결과와 알려진 문제

Git 변경 내역을 활용한 초안 자동 생성을 우선 검토하며, 최종 검토 후 개발 업데이트 탭에서 조회할 수 있도록 한다.

### 원칙 10. 모듈별 공식 문서 관리

모든 기능 모듈은 **MIG DOT Documentation**을 통해 현재 제공되는 기능과 사용 방법을 문서화한다.

Documentation은 사용자가 각 모듈의 기능을 이해하고 활용할 수 있도록 하는 공식 설명서 역할을 한다.

#### 10.1 필수 문서 구성

각 모듈의 문서에는 필요에 따라 다음 내용을 포함한다.

1. **모듈 개요:** 목적, 핵심 기능 및 사용 대상
2. **기능 목록:** 하위 기능과 제공 범위
3. **사용 방법:** 기능별 사용 절차 및 예시
4. **설정 안내:** 필요한 초기 설정과 변경 가능한 옵션
5. **데이터 안내:** 저장되는 정보와 데이터 관리 방법
6. **주의사항:** 알려진 제약, 사용 시 유의사항
7. **문제 해결:** 자주 발생하는 문제 및 해결 절차

기능의 복잡도에 따라 항목을 간소화할 수 있다.

#### 10.2 문서 계층 구조

Documentation은 모듈별 계층 구조를 따른다.

```text
Documentation
├── MIG DOT
│   ├── 시작하기
│   ├── 시스템 개요
│   └── 공통 설정
│
├── Routine
│   ├── 모듈 소개
│   ├── 루틴 등록
│   ├── 루틴 체크
│   └── 기록 조회
│
├── Game Tracker
│   ├── 모듈 소개
│   ├── 육성 목표 설정
│   ├── 재화 기록
│   └── 효율 분석
│
└── Finance
    ├── 모듈 소개
    ├── 수입·지출 등록
    └── 통계 조회
```

각 모듈은 필요한 만큼 하위 문서를 추가할 수 있다.

#### 10.3 문서 유지보수 원칙

- Documentation은 실제 배포된 기능을 기준으로 작성한다.
- 신규 기능 배포 시 해당 기능의 사용법을 추가한다.
- 기능 변경으로 사용법이 달라지면 관련 문서를 수정한다.
- 삭제된 기능은 문서에서 제거하거나 지원 종료 상태를 표시한다.
- 구현되지 않은 기능은 현재 제공되는 기능처럼 설명하지 않는다.
- 문서 변경도 Git을 통해 버전 관리한다.

#### 10.4 조회 기능

MIG DOT 내 Documentation 탭은 다음 기능을 제공한다.

- 모듈별 문서 목록
- 하위 기능별 문서 탐색
- Markdown 본문 표시
- 문서 제목 및 내용 검색
- 관련 모듈로 이동

검색은 초기에는 빌드 시 생성한 문서 인덱스를 기반으로 구현하며, 별도의 검색 서버를 요구하지 않는다.

## 4. 통합 문서 관리 체계

MIG DOT는 세 가지 공식 문서 유형을 관리한다.

| 문서 | 기록 기준 | 유지 방식 |
|---|---|---|
| Meeting Report | 개발 논의 및 의사결정 | 이력 누적 |
| Development Update | 실제 기능 및 코드 변경 | 이력 누적 |
| Documentation | 현재 제공되는 기능과 사용법 | 지속 갱신 |

### 4.1 저장 정책

모든 공식 문서는 Markdown 파일을 원본(Source of Truth)으로 사용한다.

웹앱은 빌드 시 문서를 수집하여 화면에 표시하며, 초기에는 문서 전용 데이터베이스를 구축하지 않는다.

### 4.2 문서 연결

필요한 경우 다음 관계를 연결할 수 있도록 한다.

- 회의록 → 관련 개발 업데이트
- 개발 업데이트 → 관련 Documentation
- Documentation → 해당 기능 모듈

### 4.3 기록 자동화

AI와 Git 변경 이력을 활용해 문서 생성·수정 초안을 마련한다.

다만 접근할 수 없는 대화나 코드 변경은 자동으로 기록된 것으로 간주하지 않으며, 최종 문서의 정확성은 개발자가 검토한다.

## 6. 개발 및 배포 정책

1. 새로운 기능의 필요성을 검토하고 모듈 소속을 결정한다.
2. 주요 설계 논의는 Meeting Report로 기록한다.
3. 기능을 개발하고 테스트한다.
4. 기능 변경 결과를 Development Update에 기록한다.
5. 새 기능 또는 변경된 사용법을 Documentation에 반영한다.
6. 코드 및 문서를 검증한 뒤 배포한다.
7. 문제가 발생하면 이전 정상 배포로 복구한다.

**기능 변경으로 문서 수정이 필요한 경우, 관련 문서의 갱신을 기능 완료 조건에 포함한다.**

## 8. 향후 확장 기준

다음 조건에 해당하는 모듈은 독립 프로젝트로 분리하는 것을 검토한다.

- 독립 서버 또는 실행 환경 필요
- 별도 배포 주기 및 기술 스택 요구
- 보안·데이터 격리 요구 증가
- 공통 시스템과의 결합이 유지보수에 불리해짐
- 외부 공개 서비스로 확장

단순히 기능이나 인터페이스가 다르다는 이유로 분리하지 않는다.

## 9. 최상위 개발 철학

> **MIG DOT는 필요한 도구를 개발하고, 개발 과정의 의사결정을 기록하며, 현재 기능의 사용법을 체계적으로 관리하는 지속 가능한 개인용 웹 플랫폼이다.**

모든 개발 결정은 다음 기준으로 검토한다.

1. 실제 사용에 필요한가?
2. 유지보수 부담을 줄이는가?
3. 다른 모듈에 불필요한 의존성을 만들지 않는가?
4. 최소 비용으로 장기간 운영할 수 있는가?
5. 개발 배경과 변경 이력을 추적할 수 있는가?
6. 현재 기능을 문서만으로 이해하고 사용할 수 있는가?

**최종 원칙: 실제 사용성, 지속 가능한 개발, 의사결정의 추적 가능성, 문서와 구현의 일치성을 우선한다.**
